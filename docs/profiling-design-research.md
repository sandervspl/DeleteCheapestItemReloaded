## Existing execution flows

### Events and synchronous refreshes

- `DCI.HandleEvent` is assigned directly as the frame's `OnEvent` handler. `ADDON_LOADED` initializes saved variables, registers events, hooks loot visibility, creates settings, and installs quest, loot-selection, and inventory callbacks. It is a distinct startup workload, not a steady-state scan. Settings dropdown initialization itself calls `UpdateDCIFrame(false)`, so startup can contain refreshes. [Handler and initialization](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L2602-L2672), [dropdown setup](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L2139-L2154), [handler assignment](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L2958-L2961).
- `BAG_UPDATE` and `GET_ITEM_INFO_RECEIVED` are always registered after initialization. Other registrations depend on automatic-display, combat, and window-debug options. Successful item-info events invalidate that item's cache, refresh the ignored list when appropriate, and refresh the main window if shown. Each shown-window bag event synchronously calls `UpdateDCIFrame(false)`; this path has no pending-request gate. An unseen window with low-slots automation and active loot instead queues a loot update. [Registration](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L2513-L2599), [item/bag handling](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L2674-L2690).
- Inventory errors, combat recovery, quest acceptance/rewards, trade changes, failed mail collection, and loot-roll handling can each cause updates. Handler branches are independent `if` blocks in several places: an event can reach multiple update sites, for example the shown-window bag refresh and quest-reward recheck. Record actual update counts rather than assuming one update per event. [Combat/error/loot paths](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L2692-L2824), [quest/trade/mail/roll paths](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L2826-L2937).
- User actions are additional roots: slash and broker toggles, ignore/remove/reset, settings changes, reward selection, and deletion continuation. A deletion continuation can attempt loot and synchronously refresh; a sale uses the container action and can be followed by bag events. Distinguish action initiation, confirmation acceptance, and resulting events. Do not measure the player's confirmation delay as execution time. [Slash](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L413-L431), [broker](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/Broker.lua#L6-L38), [ignore mutations](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L500-L543), [action guards and confirmation](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L1109-L1174), [delete/loot continuation](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L1867-L1920).

### Deferred and periodic work

- `QueueLootUpdate` skips scheduling when a request is already pending. Its `C_Timer.After(0, ...)` callback validates request identity, clears pending state, then calls `TryShowLootWindow`. That function can return for disabled automation, missing opening conditions, dismissal, or absent loot UI before refreshing. `LOOT_OPENED` can run both an immediate attempt and a queued attempt. Preserve these distinctions in trace records. [Loot queue and gates](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L370-L410), [event attempts](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L2784-L2810).
- `QueueInventoryVisibilityUpdate` replaces the pending token and schedules a fresh callback on every enabled request. Older callbacks return when their tokens are stale. This suppresses old callbacks' useful work but does not suppress scheduling. The surviving callback opens or hides according to bag visibility and dismissal state. Count requested, scheduled, superseded, executed, and refresh-producing callbacks separately. [Inventory queue](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L220-L243).
- The source's Forever branch adds inventory open/close registry callbacks and an `OnUpdate` watcher. The watcher returns while automation is disabled, otherwise accumulates elapsed time and checks visibility after at least `0.2` accumulated seconds; only state changes queue an update. This is not a fixed-rate ticker and it does not scan bags on every rendered frame. Count watcher invocations, actual visibility checks, state changes, and resulting callbacks separately. Client behavior/support is pending upstream research. [Client branch](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L10-L12), [registry callbacks](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L2654-L2670), [watcher](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L2963-L2985).
- Closing loot, changing options, or dismissing the main window invalidates pending work. Distinguish a callback observing invalidation from a request skipped at enqueue time. Main-frame visibility hooks also maintain dismissal state. [Invalidation on options](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L2519-L2558), [dismissal hooks](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L1189-L1208), [loot closure](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L2605-L2615).

## Alternatives and tradeoffs

Effort below is relative engineering scope, including compatibility checks and verification; it is not a delivery estimate. Overhead assessments are design expectations requiring measurement.

| Approach | Effort | Diagnostic value | Overhead and retention | Toggles/export |
| --- | --- | --- | --- | --- |
| Minimal named spans | Low to medium | Which synchronous phase is slow; count, total, mean, maximum; misses event ordering unless reason counters are included. | Two clock reads plus aggregation per span when enabled; bounded aggregates, no per-item history. Timing source and units pending API research. | Explicit start/stop/reset/report; copyable aggregate report. |
| CPU attribution | Medium, potentially high across clients | Overall addon/function CPU responsibility, subject to counter semantics; limited explanation of why a refresh occurred or time spent queued. | Instrumentation cost may extend beyond DCI; bounded snapshots/deltas, avoid continual counter polling. Availability, enablement, ownership, reset and reload semantics pending. | Separate opt-in mode; capability status and settings in export; never silently change global profiler settings. |
| Event/scan timeline | Medium | Event bursts, duplicate refresh causes, deferred latency, invalidations, combat/context transitions. | Per-record writes can dominate a burst; fixed-capacity ring with overwrite count, fixed vocabulary, no item tables. | Separate trace toggle, duration/record caps, recent-record report and copy export. |
| External-tool-only baseline | Low addon effort; medium operator effort | Establish whether DCI is a meaningful contributor before adding code; may provide addon/function costs if the selected tool supports them. Weak on DCI-specific causality unless combined with existing debug. | Zero new DCI instrumentation, but tool/profiler overhead still exists. Tool retention/export depends on a verified pinned version. | Keep entirely optional. Record tool revision, configuration and capture/export steps after sibling verification. No external tool is asserted compatible here. |
| Hybrid: spans + bounded timeline + optional external CPU capture | Medium to high overall, deliverable in stages | Distinguish expensive scans from excessive scan frequency; connect cold item resolution/provider work to user-visible stalls; corroborate with independently collected CPU evidence. | Default off; aggregates in basic mode, ring only in trace mode; CPU separately opted in. Avoid enabling every mode for ordinary play. | One command family, explicit mode/status, frozen export; support partial capabilities. |

Recommendation: stage the hybrid. First ship only explicit named aggregates plus root/reason counters; next add a bounded event/request timeline if ordering remains unresolved. Treat CPU attribution as optional and capability-gated after API research, with an external-tool-only baseline available before any implementation. Do not change scheduling, caches, sorting, or display behavior during the profiling change: those would confound comparisons.

Existing `/dci debug` is not a profiler. `TraceWindow` formats a detailed string and calls free-slot/visibility queries; verbose `DebugPrint` can recursively serialize tables. Some debug call arguments are constructed before the output threshold returns. Measure with both debug modes off by default, and label any trace-enabled run as a different capture configuration. Enabling window debug also changes event registrations. [Debug implementations](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L314-L362), [debug command](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L422-L429), [conditional registrations](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L2534-L2553).

## Proposed controls, storage, and report contract

All commands here are proposals; none currently exists.

- `/dci profile start`: fresh aggregate session, stop an existing capture first; default maximum capture duration 60 seconds, subject to verified timing support.
- `/dci profile start trace`: aggregates plus bounded timeline. Example initial capacity: 1,024 records. Report capacity, overwritten records and elapsed capture range; do not silently present the retained tail as a complete session.
- `/dci profile stop`: freeze capture without reporting in the hot path. `/dci profile status`: current mode, elapsed duration, record usage, backend/capability state. Status must not trigger a scan or open the main window.
- `/dci profile report`: short aggregate report after capture. `/dci profile export`: frozen copyable text, using a client-verified UI mechanism; no assumption that an addon can write arbitrary files. Paginate or bound output and state truncation. `/dci profile reset`: discard profile data only, leaving ordinary DCI settings intact.
- An optional `/dci profile cpu ...` command family should be designed only after sibling research resolves supported counters and settings. Unsupported modes should explain the unavailable capability without affecting basic capture or pretending missing data is zero.

Use session-local storage by default; stop/reset/reload disable collection. Do not add unbounded saved history to `DCI_DB`. Its current saved-variable declaration is per character, reset-defaults replaces the database, and verbose debug is cleared on load. If persistence is later wanted, make it an explicit export action with one bounded snapshot and schema version. [Saved-variable declaration](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.toc#L14-L16), [reset/load behavior](https://github.com/sandervspl/DeleteCheapestItemReloaded/blob/02dd1ee3b04a46bb05678344bb97909b41a47f0a/DeleteCheapestItem.lua#L2448-L2509).

Aggregate fields: fixed span name, count, inclusive total, maximum, mean, early-exit counts, root reason, and workload counts. Percentiles require a bounded sample/histogram and an explicit approximation label; omit them initially. Timeline fields: monotonic relative time and duration, event/span kind, sequence ID, parent/request ID, capture generation, context, outcome and numeric workload counts. Cap the set of names; do not use item IDs or arbitrary messages as aggregation keys. Retained trace data and aggregates have different lifetimes: aggregates cover the full session even when the ring overwrites older records.

Export metadata: schema, exact addon revision/version, interface/build identifiers, timing backend/units, mode, CPU capability/configuration if applicable, debug flags, auction provider/version when known, relevant filters/automation/full-stack/theme options, bag/slot/candidate counts, capture duration and dropped/overwritten records. Use relative durations rather than visible calendar timestamps. Avoid character identity, target GUIDs, raw event arguments, mail contents, complete item links, and localized strings in hot-path records. Export formatting occurs after capture. Keep profile mode separate from `/dci debug` and the verbose settings checkbox.

Disabled collection should avoid clock calls, string formatting, per-slot allocations and new polling work. Enabled collection should aggregate per scan rather than record every bag-slot read, comparator call, property access, or `OnUpdate` invocation. Preserve callback/function return values, early returns, errors and deletion safeguards. Instrumentation must not swallow errors or perform extra item/provider queries to populate metadata. A stopped capture must reject late callbacks from an older capture generation.

## Medium/hard in-game verification plan

These are proposed manual scenarios, not executed results. Run on each supported client after API research establishes the relevant paths. Use disposable low-value items for destructive scenarios. Save a repeatable artifact for each run: numbered steps, exact revision/build, exported profile, matching settings/workload manifest, and a short recording or screenshots showing the visible result. Record unavailable client-specific steps instead of substituting an assumed equivalent.

| Scenario | Workload and actions | Evidence and acceptance criteria |
| --- | --- | --- |
| Full bags with cold/warm item resolution | Many occupied slots, duplicate stacks, mixed qualities, ignored/quest/bound/locked items; compare first opening after reload with repeated openings and subsequent item-info events. Include vendor-only and a verified auction integration. | Counts distinguish visited/eligible/deduped/displayed items; cold lookups and later event refreshes remain distinguishable. Filter/sort results match collection-off runs. Reload alone is not proof that the game's item cache is cold; report observed lookup misses. |
| Loot error and cancellation race | Near-full bags, multiple loot slots; enable auto-loot plus low-slots, reproduce full-inventory failure, immediately close/reopen loot and manually dismiss DCI before deferred work runs. Repeat with a replacement loot UI if available. | Timeline links immediate/deferred attempts and records skipped/coalesced/invalidated requests. No stale automatic reopening; capture does not alter selected loot or dismissal behavior. |
| Inventory callback burst and combat | On Forever, exercise combined/individual bags, rapid bag toggles, automatic inventory on/off, manual DCI dismissal, combat entry/exit with AllowInCombat disabled. Repeat ordinary bag-event paths on other clients as supported. | Separate frame callbacks, watcher checks, scheduled callbacks and actual refreshes; inactive watcher work stays absent from detailed trace. Correct reopening/dismissal behavior; no held spans across the combat wait. |
| Confirmation with stale slot | During loot, request deletion with confirmation, move/replace/change quantity of the candidate before accepting; then repeat with an unchanged disposable stack. At a merchant, sell several inexpensive stacks. | Stale action is rejected by existing guards; successful deletion, loot continuation and subsequent bag-event refreshes have separate IDs. Human confirmation wait excluded from execution cost. |
| Quest and event fan-out | Full inventory while accepting an item-granting quest, then a quest turn-in with choices plus guaranteed rewards; change selection, free a slot, and trigger bag updates while rewards remain open. | Trace can represent multiple updates from one event/root; context transitions and scan counts explain the work. Same choices, visibility and slot reasoning as baseline. |
| Mail/trade and render-heavy options | Several attachments with full bags and Open All; several changing trade offers; many distinct eligible candidates, long item names, both prices and full-stack values enabled; resize and use a verified skin integration. | Action-generated event bursts are separated from row/text costs. Capture-on/off renders/actions agree. Report actual candidate count even if the character cannot supply 100 distinct candidates. |
| Retention and lifecycle pressure | Repeat medium/hard scenarios until the trace ring wraps; stop while a callback is pending, export twice, start a fresh capture, reset and reload. | Hard capacity and overwrite count verified; frozen exports stable; no old-generation records in a new capture, no saved history growth, no profiling after stop/reload. Export/status do not cause scans. |

For overhead, repeat an identical script with collection off, aggregate-only, and trace modes, then CPU/external mode separately if verified. Alternate run order, include warm-up, hold bags/settings/addons/frame-rate conditions as stable as possible, and retain all runs. Compare workload counts first; compare durations only across equivalent work. An independent compatible measurement source is needed to estimate total instrumentation overhead; DCI's own spans cannot measure their full collection cost. Do not claim a numerical overhead budget or performance improvement until measured. Separate startup/widget construction and debug-enabled captures from steady-state captures.
