Research performed 2026-11-15. This is an external-source comparison, not a recommendation about DeleteCheapestItem runtime behavior or client compatibility. No addon code was changed. The shared `.cache/wow-ui-source` checkout was neither read nor modified; no Blizzard compatibility conclusions are made here. Popularity rankings are outside scope.

## Keep the measurement types separate

| Implementation | What it measures | Counts mean | Activation and reporting |
| --- | --- | --- | --- |
| WeakAuras | Explicit `debugprofilestop()` intervals around aura/system work; separate session elapsed interval | Internal `count` is nesting depth, not invocation count | Start/stop or timed/combat/encounter capture; sortable bars and copyable summary |
| Details | Explicit `debugprofilestop()` intervals by named operation | `runs` counts starts | Swappable enabled/no-op functions; auto-enabled under a source build-number condition; dump report |
| Numy AddonProfiler | Engine `C_AddOnProfiler` addon/overall tick metrics | Threshold counters describe timing spikes; not event dispatches | Active/performance/passive modes; sortable history UI |
| Numy FunctionProfiler | Elapsed interval around wrapped calls, plus Lua heap-size difference | Completed logged calls and ticks with activity | Logging disabled initially; wrapper remains installed; sortable bounded-history UI |
| AddonUsage | `GetAddOnCPUUsage()` cumulative CPU accounting divided by elapsed seconds | No event/call count in its CPU-rate formula | `scriptProfile` toggle with reload; manual or one-second updates |

The table summarizes the pinned implementations detailed below. A bracketed stopwatch duration should be labeled elapsed execution time, not assumed equivalent to engine CPU attribution. A session's elapsed duration includes time outside the measured work. Event frequency, function-call frequency, nesting depth, and threshold-exceedance counts are different quantities. No attempt was made to benchmark overhead or independently establish engine attribution semantics from Blizzard source.

## 1. WeakAuras: explicit scopes with same-key depth protection

`StartProfiling(map, id)` creates an accumulator with `elapsed`, `spike`, `start`, and `count`. On repeated starts for an already-active key it increments `count` without resetting the timestamp. `StopProfiling` records elapsed time and maximum interval only when the depth returns to zero. Thus nested same-key scopes contribute one outer interval rather than being added repeatedly. Different keys retain independent intervals and may overlap: their sum is not automatically exclusive time. `StartProfileSystem` also opens a shared `wa` key, which uses the same depth mechanism. These are direct observations plus the overlap consequence of the implementation, not evidence of a general call-tree profiler. [Timing and nesting, lines 79-131](https://github.com/WeakAuras/WeakAuras2/blob/94bfb83e9cea0d04e53d9a656de7607d86a6b606/WeakAuras/Profiling.lua#L79-L131).

Capture can be manual, duration-limited, or armed for the next combat/encounter. Starting clears aura/system data and replaces private instrumentation functions with real implementations. Stopping records session elapsed time, installs no-op functions, unregisters capture events, and cancels the scheduled timer. Disabled instrumentation still entails existing call sites invoking no-op functions; it is not literally zero overhead. [Capture modes and start/stop, lines 152-273](https://github.com/WeakAuras/WeakAuras2/blob/94bfb83e9cea0d04e53d9a656de7607d86a6b606/WeakAuras/Profiling.lua#L152-L273).

Reporting refuses to print while capture is running, reports time inside WA relative to session duration, lists aura/system intervals, and explicitly notes incomplete aura attribution. A nonzero depth at report time is shown as an error. The UI offers a copyable summary for support. Its grouped system report adds constituent `spike` values; consequently a grouped spike is not necessarily an observed simultaneous maximum. [Report formatting, lines 290-305](https://github.com/WeakAuras/WeakAuras2/blob/94bfb83e9cea0d04e53d9a656de7607d86a6b606/WeakAuras/Profiling.lua#L290-L305), [report generation, lines 369-434](https://github.com/WeakAuras/WeakAuras2/blob/94bfb83e9cea0d04e53d9a656de7607d86a6b606/WeakAuras/Profiling.lua#L369-L434), [summary button, lines 507-508](https://github.com/WeakAuras/WeakAuras2/blob/94bfb83e9cea0d04e53d9a656de7607d86a6b606/WeakAuras/Profiling.lua#L507-L508).

## 2. Details: named stopwatch accumulators and explicit run counts

The real timing implementation is in `boot.lua`, not the settings-profile chooser named `window_profiler.lua`. Each start stores one `startTime` and increments `runs`; stop adds the elapsed difference. `petContainer.SetPetData` demonstrates actual runtime use, with start and stop bracketing its copy loop. Unlike WeakAuras, there is no same-key depth/stack here: a recursive start with the same name overwrites the outer timestamp. Distinct nested names measure inclusive intervals, and their sum can double-count work. [Implementation, lines 1964-1981](https://github.com/Tercioo/Details-Damage-Meter/blob/256a0d70146ee6a2db9b68086572ff608ca6f4c5/boot.lua#L1964-L1981), [instrumented operation, lines 73-82](https://github.com/Tercioo/Details-Damage-Meter/blob/256a0d70146ee6a2db9b68086572ff608ca6f4c5/classes/container_pets.lua#L73-L82).

Enable/disable swaps callable functions; reset wipes the cache. This revision automatically calls `EnableProfiler()` when the fourth `GetBuildInfo()` return is at least `100000`, so this is not universally opt-in. This is a source condition only, not a claim about which DCI clients satisfy it. `ProfilerResult()` formats per-name elapsed totals and start counts, sums all elapsed totals, then calls `dumpt`. A reporting pitfall: it divides stopwatch values by 1000 but appends `ms`; the displayed unit needs independent scrutiny rather than copying. `ResetProfilerResult()` is empty, whereas `Profiling.ResetProfiler()` actually wipes the cache. [Controls and report, lines 1983-2018](https://github.com/Tercioo/Details-Damage-Meter/blob/256a0d70146ee6a2db9b68086572ff608ca6f4c5/boot.lua#L1983-L2018).

## 3. Numy AddonProfiler: addon-level engine metrics with collection modes

Active mode reads overall and per-addon `LastTime` every update, adds positive values to totals, records per-tick history, and tracks maxima. Performance mode retains the per-update reads, totals, and peak tracking but omits the tick-history storage. Passive mode removes the collection `OnUpdate` callback. None of these paths creates named function scopes or an exclusive-time call tree. [Mode switching and collection, lines 446-554](https://github.com/NumyAddon/AddonProfiler/blob/bcf148b71282181a7dc3668c5c7b842a595d5bdf/AddonProfiler.lua#L446-L554).

It is enabled in active mode by default. Explicit disable freezes current metrics, hides the collection frame, and cancels its purge ticker; enable resets metrics and restarts collection. Its warning says legacy `scriptProfile` is unnecessary for this addon. This is evidence of the addon's intended operating model, not proof that engine profiling has zero cost. [Defaults, lines 370-377](https://github.com/NumyAddon/AddonProfiler/blob/bcf148b71282181a7dc3668c5c7b842a595d5bdf/AddonProfiler.lua#L370-L377), [enable/disable, lines 2736-2771](https://github.com/NumyAddon/AddonProfiler/blob/bcf148b71282181a7dc3668c5c7b842a595d5bdf/AddonProfiler.lua#L2736-L2771), [legacy profiling warning, lines 257-260](https://github.com/NumyAddon/AddonProfiler/blob/bcf148b71282181a7dc3668c5c7b842a595d5bdf/AddonProfiler.lua#L257-L260).

History supports reset, combat, encounter, challenge mode, and rolling time ranges up to 600 seconds. Threshold metrics use `CountTimeOver1Ms` through `CountTimeOver1000Ms`, which must not be described as event counts. Old history is pruned in buckets, so the 600-second horizon is not a strict per-entry allocation cap. Its UI documents which modes sacrifice history to reduce background work. No standalone profiler-report export was found in the inspected implementation; settings or arbitrary table copies should not be called report export. [Metrics and history, lines 25-60](https://github.com/NumyAddon/AddonProfiler/blob/bcf148b71282181a7dc3668c5c7b842a595d5bdf/AddonProfiler.lua#L25-L60), [bucket pruning, lines 568-600](https://github.com/NumyAddon/AddonProfiler/blob/bcf148b71282181a7dc3668c5c7b842a595d5bdf/AddonProfiler.lua#L568-L600), [mode descriptions, lines 1988-1995](https://github.com/NumyAddon/AddonProfiler/blob/bcf148b71282181a7dc3668c5c7b842a595d5bdf/AddonProfiler.lua#L1988-L1995).

## 4. Numy FunctionProfiler: opt-in wrappers, call and tick distributions

`Wrap` checks logging, takes stopwatch and `collectgarbage("count")` readings, invokes the original function, then logs elapsed and heap-size differences. Disabled logging directly calls the original function through the wrapper. The enabled path allocates a return-value table; it has no protected-call cleanup, so a thrown error bypasses logging. Local timestamps allow each invocation its own interval, including recursive calls, but there is no child-time subtraction: nested wrapped functions produce overlapping inclusive durations. Heap-size differences are not an allocation census and can reflect garbage collection. These limitations follow directly from the wrapper, not from runtime experiments. [Wrapper, lines 43-69](https://github.com/NumyAddon/FunctionProfiler/blob/71a9990ed7d77e0d37b97db4879968917294c23f/Api.lua#L43-L69).

Logging starts false, startup logging defaults false, and enabling installs a five-second purge ticker. Disabling cancels it and clears collected data and buffers, rather than freezing a report. Wrappers remain installed. The source also wraps some of its own maintenance/report-preparation functions, making profiler self-cost visible but increasing measurement perturbation. [Logging lifecycle, lines 96-134](https://github.com/NumyAddon/FunctionProfiler/blob/71a9990ed7d77e0d37b97db4879968917294c23f/Api.lua#L96-L134), [startup and self-instrumentation, lines 1006-1047](https://github.com/NumyAddon/FunctionProfiler/blob/71a9990ed7d77e0d37b97db4879968917294c23f/Profiler.lua#L1006-L1047).

The report derives call totals, average and worst call time, per-tick totals/maxima, and calls per tick from retained records. The denominator for average tick time/calls per tick is ticks represented by activity for that function, not every elapsed game frame. Retention targets 600 seconds with bucket pruning. The UI's `latestCallTime` is assigned each record's `worstTime`, so the label should not be read as proof it preserves the final individual call's timing. No standalone copy/export report path was found in the inspected files. [Aggregation, lines 16-103](https://github.com/NumyAddon/FunctionProfiler/blob/71a9990ed7d77e0d37b97db4879968917294c23f/Profiler.lua#L16-L103), [UI columns, lines 201-290](https://github.com/NumyAddon/FunctionProfiler/blob/71a9990ed7d77e0d37b97db4879968917294c23f/Profiler.lua#L201-L290), [buffering and pruning](https://github.com/NumyAddon/FunctionProfiler/blob/71a9990ed7d77e0d37b97db4879968917294c23f/BufferUtil.lua#L69-L155).

## 5. AddonUsage: cumulative CPU rate, not stopwatch timings

In the pinned `3.2.6` archive, `AddonUsage.lua` lines 172-196 call `UpdateAddOnCPUUsage()`, read each addon's `GetAddOnCPUUsage()`, and divide the cumulative values by elapsed seconds since `totals.start`, guarded against a zero denominator. This yields a since-reset CPU rate in ms/s, not last-second CPU, per-call latency, or event frequency. Lines 127-131 reset the CPU counters and run garbage collection; this reset has global measurement side effects rather than merely clearing a private display table. [Exact author release and downloadable source](https://www.curseforge.com/wow/addons/addon-usage/files/6671699).

Lines 392-403 expose a CPU checkbox whose confirmation changes `scriptProfile` and reloads the UI, with an explicit overhead warning. Lines 435-448 install/remove a continuous-update callback; `updateFrequency` is one second at line 37. Pausing that UI update does not itself turn off `scriptProfile`. There are no named nested scopes or exclusive-time calculations in this implementation, and no dedicated report-export path was found. These observations are from the checksum-pinned archive above. The author's description independently explains the CPU-rate denominator and warns about library attribution and monitoring overhead. [Author documentation](https://www.curseforge.com/wow/addons/addon-usage), [pinned source archive](https://edge.forgecdn.net/files/6671/699/AddonUsage_3_2_6.zip).

## Requested candidates that should not be mislabeled as profilers

**BigWigs and DBM:** searched the independently cloned revisions' Lua/Markdown for `debugprofilestop`, `GetAddOnCPUUsage`, `GetFunctionCPUUsage`, `profiling`, `profiler`, and `benchmark`; no concrete timing profiler was established in these checkouts. This is a bounded search result, not proof there is no profiler anywhere in their ecosystems or history. BigWigs' `API.RegisterProfile` is settings import, as shown by its profile-name/string validation and import routines; it is not CPU profiling. [BigWigs settings API, lines 222-236](https://github.com/BigWigsMods/BigWigs/blob/66439603e03d6b7d3e2786b261a769f965c130d1/API.lua#L222-L236), [DBM inspected revision](https://github.com/DeadlyBossMods/DeadlyBossMods/tree/af6967d78c3bd00143a0eaf45573859a2b40239a).

**!BugGrabber:** SVN revision 403's `BugGrabber.lua` lines 313-340 replenish a time-based message allowance and throttle errors; lines 354-398 store timestamps and increment duplicate-error counters. Those are error occurrence counts and rate limiting, not execution CPU/elapsed profiling. Lines 238-241 cap stored errors using `MAX_BUGGRABBER_ERRORS` (500 at line 34), illustrating bounded diagnostics. This is a useful separate pattern for controlling diagnostic floods, but it is not counted as one of the five timing profilers. [Pinned first-party source](https://repos.wowace.com/wow/bug-grabber/!svn/bc/403/trunk/BugGrabber.lua).

## Synthesis for the parent research task

The external implementations support several distinct patterns, without establishing what DCI should implement:

1. Swapping instrumentation functions to no-ops removes timing/storage work while retaining call-site overhead (WeakAuras and Details).
2. Same-key nesting needs an explicit policy: outermost-only depth accounting (WeakAuras), a single overwritten timestamp (Details), or independent inclusive call intervals (FunctionProfiler).
3. Aggregating overlapping scopes does not produce exclusive total cost. Similarly, adding maxima is not a measured aggregate maximum.
4. Capture duration, reset semantics, sampling interval, and denominator belong in a report's meaning: a since-reset CPU rate differs from a rolling per-tick average or an instrumented interval total.
5. Explicit stop can preserve results (WeakAuras, AddonProfiler), whereas disable can destroy them (FunctionProfiler). A copyable support report is an independently verified feature in WeakAuras, not a feature established across all examples.
6. Diagnostic collection has its own work: timer calls, table allocation, heap reads, history maintenance, and UI refresh. The sources show controls and tradeoffs; they do not supply a portable quantitative overhead guarantee.

These are inferences from the pinned implementations cited above. No in-game performance benchmark, addon compatibility validation, or DCI implementation was performed. The Markdown was checked for replacement characters, stray question marks, and other encoding corruption before handoff.
